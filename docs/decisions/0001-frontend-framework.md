# 0001. How to structure the browser interface as it grows

**Status:** Proposed · **Date:** 2026-10-25 · **Deciders:** maintainers

## Context

Pigeon's interface is rendered on the server with Go templates, with plain
JavaScript for the interactive parts. With upload links, drag-and-drop uploads,
and cancelable uploads added, it is becoming more involved, and the
[functional review](../audit/2026-10-25-features.md) lists features that add
state in the browser. This record asks whether to move to a JavaScript
framework such as React, and if so which.

### The interface today

Measured after drag-and-drop uploads and canceling (#26):

- **Scripts:** about 810 lines of JavaScript in four files: `upload.js` (458
  lines: selection, dropping, upload, progress, cancel), `shares.js` (the Share
  dialog), `dialog.js` (one dialog for every file and account action), and
  `validation.js` (form messages).
- **Templates:** about 480 lines in eleven Go templates. The sign-in page,
  explorer, administration page, and upload link page are rendered on the
  server, and their actions are forms that post and redirect. Only the Share
  dialog and upload progress use JSON; the file list refreshes by fetching an
  HTML fragment from `/files`.
- **Build:** no npm. Tailwind CSS is generated by a pinned, checksum-verified
  standalone binary, Font Awesome is vendored, and CI fails when generated
  files are out of date. Everything is embedded in the Go binary.
- **Tests:** about 1,000 lines of browser-script tests run in Node against a
  small simulated DOM, finding elements by the IDs in the templates.
- **Security:** a Content Security Policy allows only same-origin scripts and
  styles, and a test rejects inline scripts, styles, and event handlers in
  templates. `html/template` escapes everything rendered.

### Where it hurts

- **Two renderers for one view:** the file list is rendered by Go, but
  JavaScript decides when to fetch it again and keeps the upload panel's state
  beside it.
- **Coupling through IDs:** scripts and tests depend on element IDs scattered
  over the templates.
- **Messages in several places:** the text for an action lives in Go handlers,
  `dialog.js`, and templates.
- **State is coming:** sorting (F4), several items at once (F12), search (F13),
  the links overview (F3), and previews (F7) all keep state in the browser,
  which plain scripts handle poorly.

## Decision drivers

- Keep the single binary with embedded assets, and no runtime dependencies.
- Keep the supply chain small and reviewable, as the pinned Tailwind and
  vendored Font Awesome do.
- Keep the Content Security Policy strict: same-origin scripts only, no inline
  code, no `eval`.
- Keep the HTTP API usable from scripts, and document any change to it.
- Make the planned features (F3, F4, F7, F12, F13) easier to build and test.
- Let the work be done in small pull requests that each ship something.

## Options

### A. React with a bundler

React components built with Vite or esbuild, served from embedded files, with
the server reduced to a JSON API.

- **Build:** npm with a lockfile, a bundler, a CI build step, and Dependabot
  for npm: hundreds of transitive packages where there are none today.
- **API:** directory listings, file actions, administration, and errors move
  from rendered pages and redirects to JSON. The API reference documents forms
  and redirects, so scripts using it change.
- **Rewrite:** the explorer, dialogs, Share dialog, upload panel,
  administration, sign-in, and upload link pages. Upload logic carries over but
  becomes components and hooks.
- **Tests:** Vitest and Testing Library replace the Node harness; Go tests of
  rendered pages become JSON tests.
- **Security:** bundled React works with the current policy. The template
  check for inline code needs a replacement for components.
- **Effort:** two to four weeks of focused work in several pull requests that
  change how the interface is built without adding features.
- **Gains:** the most familiar model and tooling, the largest ecosystem, and
  the easiest hiring and onboarding for interface work.

### B. Preact with htm, without a build step

Preact offers React's component and hooks model in a few kilobytes. With
[htm](https://github.com/developit/htm), templates are tagged template
literals instead of JSX, so modules load directly in the browser.

- **Build:** none. Preact and htm are vendored and checksum-pinned like Font
  Awesome, and loaded as ES modules. htm does not use `eval`, so the policy
  stays as it is.
- **API:** only the widgets that move need JSON endpoints; the rest of the
  pages stay rendered by Go.
- **Migration:** one widget at a time: the Share dialog first, then the file
  list, then uploads. Each pull request ships on its own.
- **Tests:** component tests can run in Node, with a small DOM library or the
  existing harness's approach.
- **Effort:** a few days for the first widget and its endpoint, then about a
  week per larger area.
- **Gains:** a component model for the stateful features, at little cost, and a
  mostly mechanical path to React with a bundler later.

### C. htmx with server-rendered fragments

Pages stay Go templates; [htmx](https://htmx.org) replaces parts of a page with
fragments the server renders, as the file list refresh already does by hand.

- **Build:** one vendored file. The default configuration needs care under the
  policy: inline indicator styles and `hx-on` attributes must stay disabled.
- **API:** handlers return fragments for page requests and keep forms and
  redirects for scripts, so the API barely changes.
- **Fit:** sorting, search, the links overview, and refreshing after actions
  become server-rendered fragments, with the server as the single source of
  truth. Uploads, which need progress and cancel, stay in `upload.js`.
- **Effort:** about a week to move the explorer and administration pages, and
  little per feature after that.
- **Gains:** the fewest moving parts, and the best fit with Go templates and
  the current security model. Selecting several items and previews remain
  plain JavaScript beside it.

### D. Plain JavaScript in ES modules

Split the scripts into modules with shared helpers for requests, messages, and
dialogs, and keep server rendering.

- **Effort and risk:** the lowest; no dependencies.
- **Limits:** it addresses the duplication but not the state that the planned
  features bring.

## Recommendation

Not React with a bundler yet. The interface is still small, and option A's
build, API, and test rewrite would cost weeks without changing anything users
see. Choose between B and C by the direction of the interface:

- **C, htmx,** if Pigeon stays a server-rendered application with interactive
  parts.
- **B, Preact with htm,** if it is heading for a richer interface, with several
  items at once, search, previews, or offline uploads, keeping the option of
  React with a bundler once the interface clearly needs it.

Settle it with a prototype: build sorting (F4) or the links overview (F3) both
ways on real Pigeon code, and compare the code, tests, and policy changes each
needs.

## Decision

Open. Revisit when one of these comes first:

- work starts on F3, F4, F12, or F13, which each add state in the browser;
- `upload.js` or the scripts as a whole grow well beyond their current size, or
  a change to one widget repeatedly breaks another;
- someone joins who mainly works on the interface.

When decided, record the choice and the prototype's results here, set the
status to Accepted, and note the follow-up work under Consequences.

## Consequences

To be written when the decision is made. For any option, expect to update the
architecture and contributing guides, the CI workflow, and, for A and B, the
API reference.
