# Code quality and design review

Reviewed commit `845a0e1` on 2026-10-20, after all findings of the
[2026-10-17 security audit](2026-10-17-security.md) were fixed. The review covered every Go source file, the
browser scripts, the templates, and the test suite, with attention to
separation of concerns, duplication, running-time complexity, consistency, and
testability. Security was out of scope except where a design choice affects it.
Measurements were taken against a local build on the reviewer's machine; they
show trends, not absolute performance.

## Summary

The code is careful and readable. Comments explain why rather than what. The
security controls listed at the end of the security audit hold up. Filesystem access
is confined with `os.Root`, and uploads publish all at once. The test suite is
thorough (120 tests, including concurrency cases) and CI is in place. Those
strengths are worth protecting while addressing the items below.

The main debts are:

1. **Work that scales with the whole account on every request.** Storage
   usage is recomputed by walking the account's entire folder tree on every
   explorer page, upload, and new folder, and for every account on the admin
   page. Path checks re-walk every component of a path for each entry they
   touch.
2. **Two catch-all types.** `config` carries settings, dependencies, and test
   knobs, and every handler hangs off it. `store` holds the database and also
   in-memory locks, upload progress, and the rate limiter. Handlers mix HTTP
   parsing, orchestration, and domain rules; the upload handler alone is 185
   lines.
3. **Repeated boilerplate.** User row scanning, schema migrations, cookie
   construction, size units, and error-to-status mapping are each written out
   in several places.
4. **A slow, serial test suite:** 37 s, and about 280 s under the race detector
   that CI uses.

Work through the items in the recommended order, one pull request each. When
you start one, set its status to **In progress**; when it is merged, set it to
**Fixed** with the pull request number, in both the table and the item. Use

## Q1. Storage usage walks the whole account on every request

**Impact:** High · **Area:** Complexity · **Status:** Fixed in #17

**Location:** [internal/pigeon/storage_usage.go:38](../../internal/pigeon/storage_usage.go#L38),
[internal/pigeon/index.go:40](../../internal/pigeon/index.go#L40),
[internal/pigeon/upload.go:79](../../internal/pigeon/upload.go#L79),
[internal/pigeon/upload.go:172](../../internal/pigeon/upload.go#L172),
[internal/pigeon/account_access.go:28](../../internal/pigeon/account_access.go#L28),
[internal/pigeon/admin.go:48](../../internal/pigeon/admin.go#L48)

`diskUsage` walks every file and folder in the account and calls `Lstat` on
each. It runs:

- on every explorer page view (`renderIndex`), including the page shown after
  each file action;
- twice per upload: before streaming and again before publishing;
- on every new folder (`requireQuota`);
- for **every account** on every admin page view and after each admin action
  that re-renders the page.

Each of these is O(N) in the number of stored entries, while the view or change
itself touches one folder. The quota bounds N at one entry per 4 KiB (262,144
entries for the default 1 GiB, and proportionally more for larger quotas).

**Evidence:**

| Account contents | Explorer page (`GET /`) | Admin page |
| --- | --- | --- |
| Empty | 6 ms | — |
| 100,000 empty files in other folders | 250–330 ms | 225 ms |

The viewed folder was the same in both rows; only unrelated files were added.
Extrapolating linearly, a full 1 GiB account of small files takes about 0.7 s
per page view and per upload phase.

**Recommendation:** keep each account's usage up to date instead of
remeasuring it.

- The simplest form is an in-memory cache keyed by account. Fill it with one
  walk on first use, and adjust it under the account lock, which every change
  already holds:
  - publishing an upload adds `currentCharge()`;
  - a new folder adds one unit;
  - a delete subtracts the removed subtree, measured with a walk of that
    subtree only;
  - a rename or move does not change usage;
  - a purge drops the entry.
- Invalidate an entry when any of these steps fails, so the next request
  re-walks. Changes made directly on disk by an operator are then picked up
  after a restart, or by an explicit "recalculate" action.
- In-flight uploads need no reservation in the cache: the upload slot already
  lets only one upload per account stream at a time, and publishing rechecks
  the quota.
- Storing usage in SQLite would survive restarts, but it adds a migration and
  the same reconciliation problem. Start with memory.

**Done when:** explorer pages, uploads, and new folders no longer walk the
account tree once its usage is known. The admin page walks only accounts
without a cached value. Tests show that usage stays correct across upload,
new folder, delete, move, purge, failure, and restart, and that a page view
performs no walk (for example, by counting walks through a test hook).

**Resolution:** usage is cached per account and kept up to date, as
recommended.

- **Cache:** `usageCache` measures an account the first time its usage is
  needed. Every read, fill, and change happens under the account lock, which
  every change to the account's files already holds:
  - publishing an upload adds the upload's charge;
  - a new folder adds one unit;
  - a deletion subtracts the deleted item, measured just before removal;
  - renames and moves leave usage unchanged;
  - a purge drops the entry.
- **Partial failures:** a failed deletion or publication may have changed part
  of the folder, so it drops the entry, and the next request measures again.
- **Outside changes:** an entry is measured again after 10 minutes, so files
  changed directly on disk show within that time, as the README promised before
  ("the server measures everything inside each user's folder"). A large
  account is walked at most once per 10 minutes instead of on every request.
- **Admin page:** each account's usage now comes from the cache, taken under
  that account's lock (including for deleted accounts).

Two related problems surfaced:

- **Staging folders:** a measurement taken while an upload streams, for
  example after the 10 minutes run out during a long upload, would have
  counted the upload's partial files and then counted them again at
  publication. Measurements now skip staging folders entirely, which also
  made `usageExcept` unnecessary.
- **Leftovers after a crash:** a crash during an upload left its staging
  folder behind. It was charged to the user, who could neither see nor delete
  it, because the name is reserved. Startup now removes stale staging folders;
  no upload can be running then.

Tests in `storage_usage_test.go`:

- `TestUsageIsMeasuredOnceAndKeptUpToDate` writes a file directly on disk once
  the usage is cached. After an upload into a new folder, a new folder, a move,
  a rename, and two deletions, it checks that the cached value equals a fresh
  measurement minus that file. This shows the value is correct and that no
  request walked the folder. Advancing the clock then makes the next page view
  measure again.
- `TestAdminPageDoesNotCountAnUploadInProgress` lets the 10 minutes run out
  mid-upload and checks that the admin page's new measurement leaves out the
  staging folder.
- `TestPurgeAndFailedChangesForgetUsage` covers a partial deletion and a
  purge.
- `TestStaleStagingIsRemovedAtStartup` covers the startup cleanup.
- `TestQuotaCountsExistingFilesAndReclaimsRemovedFiles` used to remove a file
  directly on disk and expect the next upload to see the freed space at once;
  it now deletes through Pigeon.

Removing the line that adds an upload's charge, the line that subtracts a
deletion, or the staging-folder skip each makes at least one of these tests
fail.

Against a live server with 100,000 files in the account:

| Request | Before | After |
| --- | --- | --- |
| Explorer page | 250–330 ms every time | 215 ms on the first view, then 9 ms |
| Admin page | 225 ms | 11 ms |
| New folder and the page it redirects to | about 300 ms each | 11 ms each |

## Q2. Path checks re-walk every component for every entry

**Impact:** Medium · **Area:** Complexity · **Status:** Open

**Location:** [internal/pigeon/storage.go:120](../../internal/pigeon/storage.go#L120),
[internal/pigeon/explorer.go:60](../../internal/pigeon/explorer.go#L60),
[internal/pigeon/upload_files.go:80](../../internal/pigeon/upload_files.go#L80),
[internal/pigeon/upload_files.go:96](../../internal/pigeon/upload_files.go#L96),
[internal/pigeon/upload_files.go:168](../../internal/pigeon/upload_files.go#L168)

`storageInfo` validates a path, then calls `Lstat` on every component from the
account root down, to reject symbolic links anywhere in the path. It is called
repeatedly on paths whose parents were just verified:

- **Listing a folder:** `readExplorer` verifies the folder, then calls
  `storageInfo` for every entry, so each entry repeats the walk of its parent
  chain: O(entries × depth) `Lstat` calls.
- **Uploading:** each file is checked in `checkPath`, again in
  `newDirectories` for each missing parent, again in `currentCharge`, and again
  in `publish`. `newDirectories` and `currentCharge` call `storageInfo` once
  per missing parent, and each call walks from the root. When a new path
  extends an existing tree of depth *m* to depth *d*, that is about
  (d − m) × m `Lstat` calls per file: quadratic in the worst case. The path
  limit allows about 2,000 components.
- **File actions:** `handleFiles` checks the same folder before and after the
  action, and `manageFile` checks the source and target separately.

The explorer sort also lowercases both names on every comparison, allocating
O(n log n) strings.

**Evidence:** listing a folder of 5,000 files took 124 ms one level deep and
2,815 ms thirty levels deep.

**Recommendation:**

- Verify a directory chain once per request, then `Lstat` only the leaf. For
  listings, the `fs.DirEntry` values from `ReadDir` already report the entry
  type without following links. `os.Root` still confines every operation to
  the account, so this keeps the "no symbolic links anywhere" rule without
  re-walking.
- In `uploadBatch`, keep a per-request map of directories already verified or
  known to be missing, so each component is examined once.
- Precompute each entry's sort key once.

**Done when:** listing time no longer grows with folder depth, and per-file
upload checks are linear in path length. A test or benchmark counts `Lstat`
calls, or times a deep listing.

## Q3. `config` and `store` are catch-all types

**Impact:** Medium · **Area:** Design · **Status:** Open

**Location:** [internal/pigeon/server.go:15](../../internal/pigeon/server.go#L15),
[internal/pigeon/database.go:18](../../internal/pigeon/database.go#L18),
[internal/pigeon/quota.go:34](../../internal/pigeon/quota.go#L34),
[internal/pigeon/purge.go:11](../../internal/pigeon/purge.go#L11)

- **`config`** holds persisted settings (`dir`, `listen`, proxies, public URL),
  the shared dependency (`store`), and test-only knobs (`allocationUnit`,
  timeouts with zero-means-default rules). Every handler and most domain
  operations are methods on it (`cfg.accessAccount`, `cfg.filesFor`,
  `cfg.checkPassword`, `cfg.accounts()`), so any function can reach
  everything.
- **`store`** is named as the database layer, but it also owns two lock maps,
  the upload-progress table, and the sign-in rate limiter. None of those are
  persisted.
- **Locking** functions live in `quota.go`. The account lock is called
  `lockUploads` and its map `uploadLocks`, although it guards every account
  operation; the actual upload lock is `lockUploadSlot`.
- **`purgeUser`** is a store method that takes the lock and receives a
  filesystem callback, so the database layer coordinates locking and file
  removal.

Ownership is therefore hard to see, and new features gravitate to these two
types. The planned device-to-device features, such as short-lived QR handoff
sessions, would add another principal next to accounts. `requireAuth` and
`authentication` currently assume every caller is an account.

**Recommendation:** split by responsibility without changing behavior:

- a `server` struct holding the dependencies, with handlers as its methods;
- `settings` as plain data, with defaults resolved once at construction rather
  than in getters such as `formTimeout()`;
- `store` limited to SQL;
- an `accountLocks` type with honest names (`lockAccount`, `lockUploadSlot`,
  `lockForRemoval`);
- an `uploadTracker` for progress;
- the rate limiter owned by the authentication code;
- account lifecycle coordination, including purge's lock and file removal, in
  `accountManager`, which already exists for this purpose.

Sub-packages can follow later if the boundaries prove stable.

**Done when:** `store` contains only the database handle; locks, progress, and
the limiter have their own types; handlers no longer depend on test knobs
through `config`; and the lock names match what they guard.

## Q4. Handlers mix HTTP, orchestration, and domain rules

**Impact:** Medium · **Area:** Separation of concerns · **Status:** Open

**Location:** [internal/pigeon/upload.go:16-200](../../internal/pigeon/upload.go#L16-L200),
[internal/pigeon/file_management.go:22](../../internal/pigeon/file_management.go#L22),
[internal/pigeon/auth.go:63](../../internal/pigeon/auth.go#L63),
[internal/pigeon/auth.go:96](../../internal/pigeon/auth.go#L96),
[internal/pigeon/admin.go:83](../../internal/pigeon/admin.go#L83)

- **`handleUpload`** (185 lines) does all of the following in one function:
  - parses the content type;
  - registers progress;
  - takes the slot and the account lock twice;
  - computes the quota;
  - stages files and runs the multipart loop with per-part error mapping;
  - rechecks the quota and publishes;
  - formats the response.

  None of the upload logic can be reused (for example by a future QR handoff)
  or tested without HTTP.
- **`manageFile`** takes seven parameters and dispatches on a string action.
  The "target must not exist" check is written twice. Callers pass fields that
  only some actions use.
- **`requireAuth`** authenticates and renders each failure. It also checks
  administrators, verifies the origin, parses the form, and checks CSRF. It
  special-cases `r.URL.Path != "/upload"` to find the CSRF token, so a generic
  helper knows about one route.
- **`handleAdmin`** keeps per-action text in three separate maps (messages,
  headings, result keys), and `handleIndex` has a fourth. Adding an action
  means editing all of them.

**Recommendation:**

- Extract domain operations that take a context, an account, and plain
  inputs, and return results and typed errors:
  - an upload receiver that consumes parts;
  - separate `mkdir`, `rename`, `move`, and `delete` functions.

  Handlers then parse, call, map the error, and render.
- Replace the path check in `requireAuth` with an option that says where the
  CSRF token comes from.
- Describe admin and file actions in one table each, holding the label,
  heading, result message, and redirect key.

**Done when:** `handleUpload` fits on a screen, `requireAuth` contains no route
checks, file actions are separate functions, and each action's text is defined
once.

## Q5. Error-to-status mapping is scattered

**Impact:** Medium · **Area:** Consistency · **Status:** Open

**Location:** [internal/pigeon/http.go:27](../../internal/pigeon/http.go#L27),
[internal/pigeon/upload.go:204](../../internal/pigeon/upload.go#L204),
[internal/pigeon/shares.go:141](../../internal/pigeon/shares.go#L141),
[internal/pigeon/auth.go:63](../../internal/pigeon/auth.go#L63)

`storageError` is the intended central mapping, but at least six other places
map errors to statuses themselves: `accessUploadAccount`, `handleShares`,
`handleSharedDownload`, `handleAdmin`, `requireAuth`, and `parseForm` with
`uploadReadErrorStatus`. The same messages are written out repeatedly:
"failed to check storage usage" appears four times, "disk quota exceeded (%s
available)" twice, and "upload canceled" three times. The mappings also
disagree:

- `handleShares` turns every error other than invalid credentials into a 500
  "failed to update share link", including a canceled request.
- Canceled work is a 408 in `storageError`, but a 500 in other paths that
  don't check for it.

**Recommendation:** one function that maps an error to a status and a message,
covering storage, quota, credentials, rate limiting, cancellation, and
deadlines, and used by every handler. Define each message once. Page handlers
that render errors into a template can use the same mapping for the status.

**Done when:** status selection lives in one place, the duplicated messages
are gone, and a table-driven test covers each error kind.

## Q6. Repeated SQL scanning and migration code

**Impact:** Low · **Area:** Duplication · **Status:** Open

**Location:** [internal/pigeon/users.go:136](../../internal/pigeon/users.go#L136),
[internal/pigeon/users.go:166](../../internal/pigeon/users.go#L166),
[internal/pigeon/users.go:205](../../internal/pigeon/users.go#L205),
[internal/pigeon/users.go:238](../../internal/pigeon/users.go#L238),
[internal/pigeon/session.go:73](../../internal/pigeon/session.go#L73),
[internal/pigeon/database.go:130-160](../../internal/pigeon/database.go#L130-L160)

- The same six user columns are listed and scanned in five queries. Adding a
  column to `user` means editing all five, and a missed one fails only at run
  time.
- Schema migrations repeat a "does this column exist?" query and a
  conditional `ALTER TABLE` five times. There is no schema version, so every
  start re-runs every check, and the order of migrations is implicit.
- `deleteUser`, `recycleUser`, and `resetPassword` each delete sessions (and
  two of them shares) with their own statements.

**Recommendation:**

- A `userColumns` constant with a `scanUser` helper.
- Numbered migrations recorded in `PRAGMA user_version`, each a small function
  run once in order. Existing databases are detected by their current columns
  the first time.
- One helper that revokes an account's sessions, and optionally its shares,
  inside a transaction.

**Done when:** user columns are listed once, migrations are numbered and
tested from each historical schema, and revocation is one helper.

## Q7. Repeated cookies, units, and magic numbers

**Impact:** Low · **Area:** Duplication · **Status:** Open

**Location:** [internal/pigeon/auth.go:111-180](../../internal/pigeon/auth.go#L111-L180),
[internal/pigeon/size.go:13](../../internal/pigeon/size.go#L13),
[internal/pigeon/size.go:45](../../internal/pigeon/size.go#L45),
[internal/pigeon/quota.go:112](../../internal/pigeon/quota.go#L112),
[web/static/upload.js:48](../../web/static/upload.js#L48)

- **Cookies:** four `http.Cookie` literals repeat the same attributes to set
  and clear the session and login cookies. The sign-in handler also calls
  `sameOrigin` twice in a nested condition to decide which error to send.
- **Size units:** units are defined three times in Go (`parseSize`,
  `humanBytes`, `quotaInput`) and once more in `upload.js`. `quota.go` also
  holds HTTP header and form formatting next to locking code.
- **Magic numbers:** the token length 43 appears in `validCSRF`, `session`, and

**Recommendation:** a cookie helper that takes the name, value, path,
SameSite mode, and lifetime; one unit table shared by parsing and formatting;
a `tokenLength` constant next to `randomToken`; and quota presentation moved
out of `quota.go`.

**Done when:** each cookie attribute set, unit table, and token length is
defined once.

## Q8. Implicit contracts between Go and the browser scripts

**Impact:** Low · **Area:** Maintainability · **Status:** Open

**Location:** [internal/pigeon/upload_progress.go:54](../../internal/pigeon/upload_progress.go#L54),
[internal/pigeon/upload.go:65](../../internal/pigeon/upload.go#L65),
[web/static/upload.js:132](../../web/static/upload.js#L132),
[web/static/upload.js:200](../../web/static/upload.js#L200),
[web/static/shares.js:41](../../web/static/shares.js#L41)

- **Progress states:** the states `queued`, `preparing`, `uploading`,
  `finalizing`, `complete`, and `failed` are string literals in Go and again in
  `upload.js`. A typo on either side fails silently.
- **Shared request code:** `upload.js` and `shares.js` each define the
  `X-Requested-With` header, the fetch options, and the expired-session
  message.
- **Upload click handler:** about 150 lines with nested closures for polling,
  the progress display, and the speed and time estimate. The estimate is pure
  arithmetic but can only be tested through the whole fake page.

**Recommendation:**

- Typed Go constants for the progress states, ideally exported to the page
  (for example, in a data attribute or a small JSON block) and checked by a
  test.
- A shared script for requests, either as an ES module, which the
  Content Security Policy's `'self'` already allows, or as one small helper
  loaded by both pages.
- Move the estimate into a pure function with its own tests.

**Done when:** progress states are defined once per language and tested
against each other, the request helper is shared, and the estimate has direct
unit tests.

## Q9. The test suite is slow and its helpers are scattered

**Impact:** Medium · **Area:** Testing · **Status:** Fixed in #16

**Location:** [internal/pigeon/users.go:88](../../internal/pigeon/users.go#L88),
[internal/pigeon/users.go:139](../../internal/pigeon/users.go#L139),
[internal/pigeon/database_test.go:15](../../internal/pigeon/database_test.go#L15)

- **Run time:** `go test ./...` takes about 37 s. Under `-race`, which CI uses,
  it takes about 280 s.
- **Causes:**
  - every fixture hashes passwords with bcrypt at the default cost;
  - none of the 120 tests call `t.Parallel`.
- **Evidence:** temporarily lowering the cost to `bcrypt.MinCost` cut the
  plain run from 37 s to 16 s; the rest is mostly serial execution.
- **Dummy hash:** the hash used for unknown usernames is a hard-coded cost-10
  string. It equalizes timing only while the real cost is also 10, and
  nothing ties the two together.
- **Scattered helpers:** test helpers live in unrelated files:
  - `newTestConfig` in `database_test.go`;
  - `formRequest` and `sessionFor` in `auth_test.go`;
  - `serve` in `ratelimit_test.go`;
  - `writeStoredFile` in `files_test.go`;
  - `uploadFilesRequest` in `directory_test.go`.

**Recommendation:**

- Make the bcrypt cost a field set at construction: production uses the
  default, and tests use the minimum. Generate the dummy hash at startup from
  the same cost.
- Mark independent tests `t.Parallel()`. Tests that replace the global log
  output must stay serial, or the logger should become a dependency.
- Move shared helpers into `helpers_test.go`.

**Done when:** the race-enabled suite runs in under a minute, the dummy hash
follows the configured cost (with a test), and shared helpers live in one file.

**Resolution:** the suite runs in seconds.

- **Password cost:** `openStore` takes the bcrypt cost and builds a
  `passwordHasher` that hashes at that cost and holds a dummy hash generated
  at startup with the same cost. Production passes `defaultPasswordCost`
  (bcrypt's default, 10); tests pass `bcrypt.MinCost`. Existing hashes keep
  the cost they were created with.
- **Dummy hash:** unknown usernames are checked against the generated dummy
  hash instead of a hard-coded cost-10 string.
  `TestUnknownUsernamesCheckAHashOfTheConfiguredCost` checks that stored and
  dummy hashes share the configured cost and that production uses bcrypt's
  default.
- **Parallel tests:** 120 of the 121 top-level tests call `t.Parallel()`. The
  exception replaces the global log output; Go runs non-parallel tests before
  parallel ones, so it captures only its own requests. No test binds a fixed
  port or changes the environment.
- **Helpers:** 20 helpers used by more than one test file moved into
  `helpers_test.go`; helpers used by a single file stay there. The README's
  development section describes this.

| Run | Before | After |
| --- | --- | --- |
| `go test ./internal/pigeon/` | 37 s | 3.3 s |
| `go test -race ./internal/pigeon/` (as in CI) | about 280 s | 4.4 s |
| `-race -cpu=2`, simulating a small CI runner | — | about 8 s |

Measured on a 16-core machine. Five consecutive race-enabled runs and two
2-CPU runs passed.

## Q10. Dead code and overlapping names

**Impact:** Low · **Area:** Readability · **Status:** Open

**Location:** [internal/pigeon/filename.go:16](../../internal/pigeon/filename.go#L16),
[internal/pigeon/filename.go:70](../../internal/pigeon/filename.go#L70),
[internal/pigeon/storage.go:21](../../internal/pigeon/storage.go#L21),
[internal/pigeon/file_management.go:12](../../internal/pigeon/file_management.go#L12),
[internal/pigeon/accounts.go:55](../../internal/pigeon/accounts.go#L55)

- **Dead code:**
  - Since Go 1.24, `crypto/rand.Read` never returns an error, so the
    time-based fallback in `shortRandHex` is unreachable.
  - The same holds for the error paths of `randomToken` and
    `generatePassphrase`, and for the `errPassphraseGeneration` plumbing
    through `accounts.go` and `admin.go`.
- **Overlapping validators:** four path validators have names that don't say
  how they differ:
  - `validateUploadPath` checks generic path syntax;
  - `validateStoragePath` adds the reserved staging prefix;
  - `validateEntryName` adds "no slash" and the new-name rule;
  - `validateNewName` checks formatting characters.

  Call sites combine them by hand. `manageFile` validates the same target
  twice.
- **Unused in production:** `listUsers` is used only by tests.

**Recommendation:** remove the unreachable branches; rename the validators by
purpose (for example `validatePathSyntax`, `validateExistingPath`,
`validateNewEntryName`) so each call site uses exactly one; delete or inline
test-only production functions.

**Done when:** no unreachable error handling remains for `crypto/rand`, each
path is validated by one clearly named function per call site, and production
files contain no test-only helpers.

## Q11. Smaller efficiency issues

**Impact:** Low · **Area:** Efficiency · **Status:** Open

**Location:** [internal/pigeon/assets.go:43](../../internal/pigeon/assets.go#L43),
[internal/pigeon/upload_progress.go:44](../../internal/pigeon/upload_progress.go#L44),
[internal/pigeon/quota.go:59](../../internal/pigeon/quota.go#L59),
[internal/pigeon/upload.go:68-95](../../internal/pigeon/upload.go#L68-L95)

- **Asset ETags:** `handleAsset` hashes each embedded asset with SHA-256 on
  every request, although embedded files never change while the server runs.
- **Progress cleanup:** `beginUploadProgress` scans every progress record to
  expire old ones each time an upload starts.
- **Lock maps:** the maps behind the account and slot locks gain one entry per
  account and never shrink, even after a purge.
- **Upload directory:** the upload handler opens the account root only to
  create the folder, closes it, and then `newUploadBatch` opens the same path
  again with `os.OpenRoot`, bypassing `userStorage.open`'s checks. The handler
  also handles raw directory paths that `userStorage` is meant to own.

**Recommendation:** compute asset ETags once at startup; expire progress
records when an upload finishes or on a timer; delete lock entries when an
account is purged; pass the opened `*os.Root` into `newUploadBatch`.

**Done when:** each item is addressed or explicitly accepted here.

## What to keep

These choices work well; preserve them while refactoring:

- **Confinement:** `os.Root` confines every filesystem operation, and
  `storageInfo`'s symbolic-link rule is enforced in one place, even though it
  is called too often (Q2).
- **Uploads:** they are staged and published all at once, with rollback.
- **Accounts:** `accountManager` already separates account changes from HTTP
  and templates, and is the natural home for more of that logic (Q3, Q4).
- **Dialogs:** `dialog.js` describes each action declaratively in one table,
  which is the model suggested for the server-side action text (Q4).
- **SQL:** queries are short and parameterized, and run on a single connection
  that serializes transactions.
- **Comments:** they explain intent and constraints rather than restating the
  code.
- **Footprint:** the dependency set is small, with CI checks for formatting,
  `go mod tidy`, `govulncheck`, and generated assets.
